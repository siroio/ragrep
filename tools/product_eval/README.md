# 文書検索の製品評価

対象は、開発者が日本語・英語の設計書や運用手順から根拠を探すローカルCLI/MCPの利用です。Goのコード検索は別評価とし、この結果でコード検索の品質を保証しません。

同梱のHarborQueue文書は、この評価のために作成した架空のサービスの資料です。第三者文書の転載や実サービスの仕様ではありません。24問の小さな固定回帰セットであり、実利用者の独立したホールドアウトではありません。これだけで製品全体の精度を主張しないでください。

## 製品の目的と次の評価方針（2026-09-09）

主目的は、会話へ必要十分な根拠だけを渡し、無関係な情報や重複で文脈を薄めないことです。その結果として、回答品質を保ちながら入力トークンを削減します。条件・例外・出典を失う切り詰めや、必要な根拠を落とす件数削減は成功としません。

- 候補を軽く確認し、必要な本文だけを取得する既存の流れを起点にする。追加取得は不足した根拠を補うために行い、既に渡した内容の重複を避ける。
- 同じ質問・モデル・設定で、通常の文書探索とragrepを使う探索を比較する。正答要件・全根拠の充足・出典の正確さを維持できることを、削減効果を評価する前提とする。
- 最終回答までの検索・本文取得・再検索・履歴の再入力を含む、全リクエストの実測入力トークンを比較する。総トークン・キャッシュ入力・所要時間・ツール呼び出し数も併記し、文字数をトークン数の代用にしない。

2026-09-08の測定は検索品質の基準値であり、この目的に対するトークン削減を実証したものではありません。以下の初回評価手順・基準と既存の結果は、その測定時点の記録として保持します。

## 測るもの

回答の既知の失敗は `answer_regressions_fixtures.jsonl` に固定しています。意味の改変、条件の脱落、回答言語の不一致と、忠実な回答の対照例を含みます。`answer_regressions.py prepare --fixtures tools/product_eval/answer_regressions_fixtures.jsonl --output blind.json` で期待結果を除いた採点入力を作り、独立した人またはLLMが各項目を採点します。`gate --fixtures tools/product_eval/answer_regressions_fixtures.jsonl --grades grades.json --output gate.json` は期待した違反の検出と正しい回答の通過を検証します。単語一致による自動意味判定ではありません。2026-09-10の独立した採点では失敗4件を検出し、対照4件が通過しました。これは採点手順の回帰確認であり、検索スキルの改善結果ではありません。

- 同じ索引・質問・kで `search --json --mode text` と `hybrid` を比較する。
- 根拠再現率: 質問ごとの必要根拠のうち上位k件に含まれた割合。
- 全根拠取得率: 必要な根拠をすべて取得できた質問の割合。複数文書の質問も、一つ見つけただけでは成功にならない。
- MRR: 最初の正解根拠の順位の逆数。正解なしの場合は0。
- 時間: CLI起動から終了まで。各モードの初回ウォームアップを別記し、その後3回の中央値・p95を測る。モデルの初期化時間が混ざる従来の `ragrep eval` の時間と比較しない。
- 取得量: 候補件数、snippetの文字数、標準出力のUTF-8バイト数。これらをLLMトークン数と呼ばない。
- 答えなし: 候補が出た割合だけを別集計する。検索には回答を控える機能がないため、候補が出たこと自体を誤答としない。断定の適否は回答評価で確認する。

モデルやCLIの失敗、壊れた出力、古い索引は環境・実行エラーです。検索ミスとして分母に混ぜず、測定を無効にします。文書番号だけでなく段落を指定した根拠を優先します。

## 初期の品質基準

以下は初回の測定を見る前に定める、この小さな回帰セットに対する暫定基準です。品質改善後に結果に合わせて緩めないでください。

| 対象 | 条件 |
|---|---|
| 実行の有効性 | エラー0、stale 0、欠測0。質問・コーパス・実行バイナリをハッシュで固定 |
| hybridの根拠取得 | k=5で平均根拠再現率 >= 0.90、全根拠取得率 >= 0.85 |
| 識別子検索 | 全根拠取得率 = 1.00 |
| 全文検索との比較 | hybridの根拠再現率がtextより0.05超悪化しない |
| 対応する開発PCでの応答 | ウォーム後のCLI応答p95 <= 1000ms。測定環境を記録し、別のハードウェアへ一般化しない |
| 小規模な回答比較 | 同じ軽量モデル・質問・コンテキスト上限でtext/hybridの根拠から回答。正答要件の充足と出典、資料にない断定を確認。未提供のトークン数はnull |

公開品質の保証には、実利用の質問を別途集めて独立に正解付けしたセット、より大きな文書群、対応環境での繰り返し検証が必要です。同梱ケースを使って調整した後のスコアを、未見データでの精度として扱わないでください。

## 再現手順

Python 3.10以降と、モデル取得済みのragrepを使います。評価用に別の作業ディレクトリを用意し、`corpus` 内の文書だけをそこへコピーします。質問・正解・測定結果は索引に入れません。

この測定ツールのコーパス指紋は `.md` / `.txt` / `.rst` を対象とします。評価ディレクトリには対象文書と隠しディレクトリ内の索引だけを置いてください。他の形式や変換コマンドを使うコーパスの再現性検証は、このパイロットの対象外です。`--modes text` で全文検索だけを実行できます。出力先に既存ファイルは指定できません。

```powershell
# $evalRoot は、この評価専用に新規作成したディレクトリの絶対パス
# $ragrep は今回ビルドした実行ファイルの絶対パス
Copy-Item tools/product_eval/corpus/*.md $evalRoot
& $ragrep index --db "$evalRoot/.ragrep/index.db" $evalRoot
python tools/product_eval/evaluate.py --ragrep $ragrep --root $evalRoot --db "$evalRoot/.ragrep/index.db" --cases tools/product_eval/cases.jsonl --output result.json --k 5 --repeats 3
python -m unittest discover -s tools/product_eval -p 'test_*.py'
```

すでに常用daemonがある環境では、評価用のユーザーキャッシュ・設定ディレクトリと空きポートを使います。このリポジトリでは `go -C src build -ldflags '-X main.daemonBindAddress=127.0.0.1:0' -o <評価用実行ファイル> ./cmd/ragrep` で評価用の空きポートを割り当てられます。Windowsでは評価プロセスの `LOCALAPPDATA` と `APPDATA` を評価専用ディレクトリに向け、必要なモデルとランタイムだけをキャッシュへコピーします。常用daemonの停止や既存DBの置換は不要です。

`result.json` の生の検索結果を残し、同じ失敗を再確認できるようにします。回答比較では一つの質問とその検索で取得した根拠だけを、新しい回答者セッションに渡します。複数質問をまとめると別質問の根拠を使えてしまうため、質問ごとの比較には使いません。正解要件は採点者だけに渡します。

モデル名・推論設定・質問・プロンプト・出力・実測時間・利用量の原記録を保存します。キャッシュ入力は入力トークンの内数、推論出力は出力トークンの内数として別記し、合計へ二重加算しません。今回のセッション単位の利用量には共通のツール定義・プロンプトの費用も含まれます。検索結果の文字数や最終リクエストの利用量と区別してください。

小標本の比較は記述的な観測であり、統計的な優位性を意味しません。回答生成の測定は事前取得した文脈からの回答で、自律的に追加検索するエージェント全体のベンチマークではありません。
